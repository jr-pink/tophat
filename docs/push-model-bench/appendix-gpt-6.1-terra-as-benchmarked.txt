AUDIT RULES (found by replaying this prompt on real packets; each one is a mistake that actually happened):
1. Threads stay separate. The header of each record group names its thread and source. A fact belongs to the thread whose record states it. Do not attach a person, project, machine or topic from one thread to a record in another thread unless that record itself names it; consecutive records from different threads are unrelated by default. A message in a group thread is a group message: never write it as something said to the owner alone, and never write that someone thanked or told the owner something when the record is addressed to the group. A tapback or reaction line (Emphasized, Loved, Liked, Laughed at "text") is a reaction to someone else's message: the reactor did not say that text.
2. Read HISTORY and the recent notes before writing "owed", "awaiting", "not yet" or "no result is recorded". HISTORY records dated after an arrival show what the assistant already answered, found or did. If the owner asked something and a later HISTORY record shows the assistant answered it, the answer is a note and there is no new open work. Open work "assistant owes the owner X" only when nothing later in the packet delivers X. When the owner replies "no", "ok" or "nah" to an assistant question that HISTORY shows, record his answer as the decision it is.
3. Quote what is unclear. A word that looks misspelled or mis-transcribed (a misspelled product, a mis-heard place, a dictated name) stays in quotes as written, with at most "probably X" if the packet itself settles it. Never replace it with a guessed word and never build a fact on the guess. A dictated, unpunctuated message may name several people: attach each description to the person the words belong to, and if you cannot tell, say so.
4. Short owner messages carry facts. "re-order", "is the server back up?", "no thats the other address" each get a dated note of what he asked, decided or corrected, even when the assistant answered in the same minute.
5. Receipts, payment confirmations, order and delivery notices, premium or payment failures, shipping-address requests, fire counts of a recurring goal, and bank notices to the owner are facts: write the merchant or counterparty, the amount, the order or policy number, the status and the date. Verification codes: note only that one was sent and when, never the value.
6. A contact-card record (a name with phones, emails, an organization or a description) is one note per person stating the name, each phone or email and the organization or description exactly as given.
7. Wake rules. (a) A record whose source is "webchat" never wakes: the owner is already in conversation with an agent there; write "wake": [] for it. (b) One wake per distinct ask per thread, on the record that carries it; consecutive messages of one burst about one subject are one wake. (c) Never wake on lines the system produced ("The server restarted and cut your last run off...", "This is an automated deployment smoke test...", "[Automated event ...]", watcher or goal output), on text the assistant or a bot wrote, or on a message that only reacts or corrects ("no thats the other address", "ok"). (d) Do not wake on an ask a later HISTORY record shows was already answered or done. (e) A counterparty's question, a bill, a payment problem, a delivery problem, or a time agreed by someone other than the owner does wake.
8. Output exactness. Use only codes printed in this packet. One code per array element ("R2", "R3"; never "R2-R3"). Note "entities" hold only E codes or "$" refs, never W, N, R or H codes; "note_refs" hold only N codes. A new work item takes a "$" ref, never a W number you invented. Output exactly one JSON object and no prose.

TERRA-SPECIFIC (round 2): this model's notes were almost always supported; its weaknesses were recall and entity names.
- Before you finish, walk the ARRIVALS once more and for every record that is neither in a note's "sources" nor in "skipped" add the note or the skip. Receipts, delivery notices, payment confirmations, failed-payment notices and bank notices are notes, not skips. A failed payment, an unmatched receipt in the bookkeeping tool, or a counterparty's question put to a colleague with the owner on cc is a wake.
- Every-entity does not mean every phrase. A NEW entity ("$" ref) must carry a proper name that the records use for the thing: a person's name, an organization, a product or model, a place, a project or document with a title. Phrases that only describe something ("the reader", "her website", "the guest pictures", "a robot", "the cal invite", "a triathlon", "the notes dashboard") are never entity names: put the exact phrase in "mentions" of the entity it points to (an existing E code, or a properly named new one), and if nothing properly named exists, create no entity for it and attach the note to the nearest named one. The store refuses a whole batch that contains one description-named entity.
