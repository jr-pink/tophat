AUDIT RULES (found by replaying the intake prompt on real record batches; each one is a mistake that actually happened):
1. Threads stay separate. A fact belongs to the thread whose record states it. Do not attach a person, project, machine or topic from one thread to a record in another thread unless that record itself names it; consecutive records from different threads are unrelated by default. A message in a group thread is a group message: never write it as something said to the owner alone. A tapback or reaction line (Emphasized, Loved, Liked, Laughed at "text") is a reaction to someone else's message: the reactor did not say that text.
2. Quote what is unclear. A word that looks misspelled or mis-transcribed stays in quotes as written, with at most "probably X" if the records themselves settle it. Never replace it with a guessed word and never build a fact on the guess. A dictated, unpunctuated message may name several people: attach each description to the person the words belong to, and if you cannot tell, say so.
3. Short owner messages carry facts. A one-line question, decision or correction ("re-order", "is the server back up?", "no, that is the other address") gets a dated note of what was asked, decided or corrected.
4. Receipts, payment confirmations, order and delivery notices, payment failures, shipping-address requests and bank notices are facts, not records to skip: write the merchant or counterparty, the amount, the order or policy number, the status and the date. Verification codes: note only that one was sent and when, never the value.
5. A contact-card record (a name with phones, emails, an organization or a description) is one note per person stating the name, each phone or email and the organization or description exactly as given.
6. Output exactness. Use only codes printed in this batch. One code per array element ("R2", "R3"; never "R2-R3"). Note "entities" hold only E codes or "$" refs; "sources" hold only R codes. Output exactly one JSON object and no prose.

MODEL-SPECIFIC (gpt-6.1-terra): this model's notes were almost always supported; its weaknesses were recall and entity names.
- Before you finish, walk the RECORDS once more: every record that carries a durable fact and is in no note's "sources" gets its note. Receipts, delivery notices, payment confirmations, failed-payment notices and bank notices are notes, not skips.
- A NEW entity ("$" ref) must carry a proper name that the records use for the thing: a person's name, an organization, a product or model, a place, a project or a document with a title. Phrases that only describe something ("the reader", "her website", "the guest pictures", "a robot", "the cal invite") are never entity names: attach the note to the entity the phrase points to (an existing E code, or a properly named new one), and if nothing properly named exists, create no entity for it and attach the note to the nearest named one.
